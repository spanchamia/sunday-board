## 1. Where things stand (baseline snapshot, 2026-10-07)

**What it is:** a single-page household app — meal plan, foods/recipes, shopping
cart, a supply/ingredient library, calendar, and tasks. No server, no framework,
no dependencies. All data lives in the browser's `localStorage`.

**How it's built**

| Piece | Role |
|---|---|
| `src/sunday-board.html` (~4,800 lines) | The real source: CSS, HTML and one big vanilla-JS IIFE |
| `src/data/ingredients.txt` | 1,896 ingredients with 12 nutrients/100 g (cooked forms derived at runtime → ~5,300) |
| `src/data/supplies.txt` | 5,053 household supplies, generated by `src/gen_supplies.py` |
| `src/build.py` | Injects both data tables into the source → writes `index.html` (generated, ~11.7k lines) |
| `tests/` | 21 Playwright scripts that drive the built page in Chromium |
| `docs/` | Screenshots used by the README |

**Golden rule:** never hand-edit `index.html`. Edit `src/sunday-board.html`, then run
`python3 src/build.py`.

**Views (left rail):** Meal plan · Foods · Shopping · Library · Calendar · Tasks.
Navigation is `go(view)` which shows one `<section id="v-…">` and calls its
`draw…()` function. Rendering is "redraw the whole view from `state`".

**State model** (one JSON object per board, see `normalise()`):

| Key | Holds |
|---|---|
| `profile` | name, email |
| `events` | `{id, title, notes, startAt}` |
| `tasks` | `{id, title, notes, dueAt, done, rep:{kind,days}, times}` — 7 repeat kinds |
| `foods` | dishes: `{id, name, ingredients[{name,qty,unit}], slots[]}` |
| `meals` | plan entries: `{id, foodId, date, slot}` (breakfast/lunch/dinner/snack) |
| `cart` | `{key, name, amount, own, bought, rep?}` |
| `repeats` | auto-shopping: `{id, name, amount, every, day, dom, from, last}` |
| `myItems`, `myCats`, `kept`, `myShelves`, `bought` | the user's own library items/shelves, stars, purchase counts |
| `targets` | nutrition targets |
| `alerts`, `fired`, `desktop` | reminders and notification state |

Every mutation calls `touch()` → saves to `localStorage` immediately (encrypted
with AES-GCM if a passcode is set), then tries a debounced "cloud" publish.

**Things worth knowing before changing anything**

1. **It was built as a Claude artifact.** `getNs()`/`pushUp()` call
   `window.claude.use('artifact')` to publish `data/board-<slug>.json`; the gate text
   says "private to your Claude account". Opened from GitHub Pages or a local file,
   that path silently no-ops, so in practice **data is device-only, no sync**.
2. **Multiple boards per device**, keyed by a slug of the name. Not real accounts —
   the email is just a label; the only security is the optional passcode.
3. **Reminders** only fire while the page is open (30-second `sweep()`); missed ones
   from the last 12 h appear on return.
4. **Repeats catch up on open** (up to ~2 months back), since nothing runs while closed.
5. **One big file.** Fine for now, but every feature touches the same ~4.8k-line IIFE.
6. **Fonts** load from Google Fonts — the only network dependency.

**Run / test**

```bash
python3 src/build.py                 # rebuild index.html
python3 -m http.server 8099          # then http://localhost:8099
cd tests && npm install && npx playwright install chromium
npm run serve   # (other terminal) then e.g.  npm run cart / npm run planner
```

   - **Home screen tiles:** Kitchen, Meals, Meal Plan, Shopping list, Stores, Home,
     To dos. **Bottom bar:** Home, Shopping List, Profile. Phone-first layout, dark theme.
   - **Item model:** meta-category → category → item. *Home* lists every category
     (Bathrooms, Cleaning, Gardening, Grilling, Pool, School, Summer, Tools,
     Toiletries…); *Kitchen* shows the food subset (Vegetables, Pantry, Spices, Farsan,
     Frozen, Dairy…). Two levels only; categories are shared between views, not nested.
   - **Items are the family's own curated list** (tens per category, not thousands),
     which is G6 in practice. Some duplicates (e.g. "Cilantro" twice). Each row has a
     shopping-list icon.
   - **Meals:** family-specific meal categories (School lunch, School snack, Special
     occasions, Breakfast, Lunch, Dinner, Snack, Salad, Dessert). Each has *Dishes*
     (Aloo paratha, Biryani, Chole…) and *Items* (ready-to-eat sides like yogurt,
     pickle). Each dish row has a shopping-list icon.
   - **Meal plan:** rolling 7 days from today, "Create a plan" per day, and
     "Create shopping list" for the week.
   - **Shopping list:** search to add, plus *Recommended items* (frequent buys).
   - **Stores:** 12 real stores (Costco, Safeway, Trader Joe's, Ranch 99, Indian
     store, Farmer's market, Amazon, Target, Home Depot, Ace, Pharmacy, Foothill
     produce). The store concept from G1 already exists.
   - **To dos:** empty. **Profile:** "Edit Family Profile" exists (G2 intent) but
     didn't open.
   - **Takeaways for the new build:**
     - Keep: tiles + bottom bar on phone, curated items, stores, meal-category →
       dishes + ready items, one-tap "add to shopping list".
     - Fix: make categories a real tree; replace Sunday Board's fixed 4 meal slots
       with family-defined meal types (e.g. school lunch); dedupe items; speed.
     - Migrate: this family's real items, dishes and stores. Owner is exporting the
       data from Firebase (pending).

## 3a. Design notes (reasoning behind the plan)

**Why a fresh build.** The current app saves each board as one JSON blob in one
browser. With a shared family board, two people editing at once would overwrite
each other. A synced app needs one database row per cart item, task, meal, etc.
That plus auth, a backend and phone/tablet layouts changes the foundation, so we
build new and port the useful parts: ingredient/supply data (becomes the global
catalogue in the DB), nutrition derivation, task/item repeat logic, shelf tree.

**Backend: Supabase (leaning).** Postgres + auth + realtime + row-level security
(each family sees only its own rows). The data is relational (families, members,
shared dish catalogue), which suits Postgres. Alternative: Firebase/Firestore,
whose offline sync is stronger (useful in a store with poor signal). If Supabase,
offline support for the shopping list needs deliberate work.

**Delivery: installable web app (PWA).** "Add to Home Screen" on phones and the
kitchen tablet; no app store needed at first. Can be wrapped for app stores later.

**Hosting (see Open questions).** Front end on Cloudflare Pages (free, commercial
use allowed, deploys on push). Vercel's free plan is non-commercial only. Backend on
managed Supabase: free to build/test (pauses after 7 idle days), Pro ~$25/mo for
real families. Self-hosting on a VPS rejected for now: backups, security and
uptime would become our job.

**Per-goal thoughts**
- G1 savings: needs usual store per item, pack/bulk size, and a rough stock level.
  Start with plenty / low / out, not exact quantities. Shopping list splits by store
  and flags items that will run out before the next warehouse trip.
- G6 + G7 are one feature: *My Home › Kitchen › Pantry / Vegetables / Fruits…* is the
  family's own catalogue; the global library is where items are picked from.
  Onboarding makes or breaks it, so offer starter templates ("typical kitchen").
- G8: family dishes private by default, published on request; importing makes a
  copy the family can adapt. Later: paste a recipe's text/link and auto-fill it.
- G9: a dish carries prep steps with lead times ("soak chana, 12 h before").
  Planning the meal creates linked tasks; moving/removing the meal updates them.
- G2 personal tasks: a "family / just me" visibility setting per task.
- G4/G5: phone gets an in-store shopping mode (big tick targets); tablet gets a
  landscape week view and a "today" view readable from across the room. Both are
  new screens, not tweaks to the desktop-first layout.
- Shared dish library comes last: it pays off only once families are using the app.

## 8. Open questions

- **Backend:** Supabase (Postgres, auth, realtime) vs. Firebase (Firestore, strong offline sync) vs. other?
- **Hosting (proposed):** front end on Cloudflare Pages (free, static, auto-deploy from GitHub); backend on Supabase managed (free tier to start, Pro ~$25/mo once real families rely on it, since free projects pause after 7 days idle); optional custom domain ~$10–20/yr. To confirm.
- **Data model:** move from one JSON blob per board to one row per item (needed so two people editing at once don't overwrite each other).
- **Stock tracking depth:** simple status (plenty / low / out) or real quantities?
- **Shared dishes:** import as a copy (family edits freely) or keep a link to the original? Moderation?
- **Existing data:** do any real boards exist that need migrating?
